# Orchestrator 与多Agent群聊设计

## 一、我最想表达的核心方向

这套设计不是单纯做一个“很多 Agent 一起说话”的群聊，而是要把两种能力结合起来：

- 开放式多角色群聊
- 把某类任务委托给内建专用子代理

也就是说，这个系统既要有“群聊的开放性”，又要有“任务执行的秩序感”。

我更偏向的最终形态是：

- 用户可以和所有子 Agent 聊天
- 用户也可以直接给某个子 Agent 下发任务
- 用户也可以只和主 Agent 聊天，由主 Agent 规划并控制子 Agent 完成任务
- 所有 Agent 的唤醒方式统一通过 `@` 完成

这里最关键的一点是，系统不是只支持一种交互模式，而是同时支持两种模式共存：

- 面向用户体验，它是开放式多角色群聊
- 面向系统执行，它是主 Agent 编排 + 子 Agent 执行

## 二、主 Agent 和子 Agent 的关系

在这套设计里，主 Agent 和子 Agent 不是平级抢答关系，而是“可直接对话 + 可统一调度”的混合关系。

### 1. 用户和子 Agent 的关系

用户可以直接 `@` 任意子 Agent，与它聊天、追问、讨论细节，或者直接向它发放任务。

这意味着子 Agent 不是隐藏在系统背后的内部能力，而是用户可直接接触的协作角色。

### 2. 用户和主 Agent 的关系

用户也可以直接 `@Orchestrator`，让主 Agent 负责：

- 理解整体目标
- 拆解任务
- 选择子 Agent
- 安排执行顺序
- 跟踪执行进度
- 汇总最终结果

也就是说，主 Agent 更像一个总调度中心，负责把用户的目标变成一张可执行的计划表。

### 3. 最核心的分工

- 主 Agent 负责规划、调度、控制
- 子 Agent 负责具体执行
- 用户既可以直连执行者，也可以通过总调度者来控制全局

这就是这套设计最核心的协作关系。

## 三、统一唤醒方式

我希望整个系统只保留一种统一唤醒入口，就是 `@AgentName`。

规则非常简单：

- `@Orchestrator`：唤醒主 Agent
- `@某子Agent`：唤醒对应子 Agent
- 没有显式 `@` 时，可以默认让主 Agent 接管

这样做的意义是：

- 用户不需要记忆多套命令体系
- 普通聊天、任务下发、调度控制都可以通过同一入口完成
- 前端交互和后端路由逻辑都更统一

## 四、为什么这里必须有强记忆机制

如果系统采用这种“开放式多角色群聊 + 所有 Agent 共享消息流”的设计，那就不能再用普通单会话 Agent 的思路来处理上下文。

原因很明确：

- 群聊历史通常不会清除
- 不能像普通开发那样随时新建一个干净 session
- 所有 Agent 的历史消息在这个系统里是共享的
- 随着时间增长，聊天内容、任务状态、执行结果会持续堆积

所以这里必须设计一套非常强的记忆机制。

这套机制的重点不只是“记住更多内容”，而是“能长期工作且不会失控”。

## 五、记忆机制最重要的不是存储，而是压缩

在这个系统里，真正的难点不是把消息存下来，而是如何把持续增长的共享历史压缩成仍然可用的上下文。

所以这里要重点设计压缩机制，而不是只做普通聊天摘要。

我认为至少要坚持下面几个原则：

- 原始历史可以长期保留，作为完整事件源
- 模型每次真正使用的上下文必须是压缩后的工作视图
- 共享消息流不能直接等于模型输入
- 压缩时要优先保留任务状态、关键决策、当前目标和执行结果
- 不能让所有 Agent 每次都去重读整段群聊历史

也就是说：

- 聊天历史是底账
- 压缩后的工作上下文才是执行输入

## 六、主 Agent 的调度不应只是“临时派活”

主 Agent 的调度规则，我更倾向于设计成一套明确的计划执行机制，而不是在群聊里随说随派。

更合适的理解是：

- 主 Agent 先规划出一张计划表
- 再由一条独立的执行控制流按顺序推进这张计划表

这里不一定非要在文档里写死成“线程”，但本质上应该有一个专门的计划执行器去运行主 Agent 的规划结果。

## 七、计划执行器应该怎么工作

我希望主 Agent 规划好的计划表，是从上往下线性推进的，但计划表内部允许区分同步任务和异步任务。

### 1. 同步任务

同步任务只能一步一步执行。

也就是说：

- 前一步没完成，后一步不能开始
- 需要严格按顺序推进
- 更适合高依赖、高冲突、需要确认上下游结果的任务

### 2. 异步任务

异步任务可以放在一起并发执行。

也就是说：

- 只要依赖满足，就可以同时启动多个子 Agent
- 更适合边界清晰、互不冲突的任务
- 主 Agent 负责统一跟踪这些并发任务的状态

所以整个计划执行逻辑可以总结成一句话：

- 主线线性推进
- 局部并发执行

## 八、执行中的用户控制权

即使主 Agent 已经开始控制子 Agent 执行计划表，用户也不应该被排除在外。

执行期间，用户仍然应该可以继续和主 Agent 交流，并控制当前计划。

至少要支持这些控制动作：

- 查询当前进度
- 停止当前计划
- 暂停当前计划
- 修改当前计划

这意味着主 Agent 不是一个“确认后就自动跑到底的黑盒”，而是一个在执行期间仍然对用户开放控制权的调度中心。

## 九、为什么执行前必须先确认

如果主 Agent 一规划完就立刻启动执行，会有很大风险：

- 可能一下子唤醒多个子 Agent
- 可能直接创建多个 Sandbox
- 可能开始修改代码、文档或 Proposal
- 一旦方向错了，回滚成本会变高

所以我更倾向于把“执行前确认”设成默认规则。

也就是说：

- 主 Agent 先产出计划
- 主 Agent 把计划给用户确认
- 用户确认后，计划执行器再正式启动

这一步很关键，因为它把“聊天中的讨论”与“真正开始执行”分开了。

## 十、为什么修改计划要终止并回退

如果用户在执行过程中要求修改计划，我不希望系统边执行边无约束漂移。

更合理的方式是：

- 一旦要修改计划，先暂停当前计划的继续推进
- 保留已经完成且仍然有效的步骤
- 以当前最后一个有效检查点为起点，重新规划后面的步骤
- 再基于新的要求生成一版后续计划
- 必要时再由用户确认，然后从该检查点继续执行

我更想强调的是这种控制逻辑：

- 计划一旦开始执行，就应该按既定版本推进
- 如果中途要改，就不要在旧计划上继续无约束漂移
- 而应该基于当前已完成的有效结果，对后续规划做增量重建

只有当核心目标、基础前提或关键依赖已经失效时，才需要终止整张计划并做全局重规划。

这会让系统的执行路径更清楚，也更便于追踪和审计。

## 十一、任务失败后不应默认整张计划重来

主 Agent 在执行计划时，还要处理另一类情况：某个步骤执行失败。

例如：

- 一个测试任务失败
- 一个构建任务失败
- 一个研究任务没有得到预期结果

这里我更倾向于的规则是：

- 不要默认“等全部跑完再重规划”
- 也不要默认“某一步失败就整张计划从头重来”
- 而是先判断失败影响范围，再决定是否继续、局部重规划或全局重规划

更合理的失败处理方式应该分成三类：

### 1. 可忽略失败

如果某一步失败不会阻塞主流程，只是一个低优先级或附加性质的结果失败，那么可以：

- 记录失败
- 保留当前计划主体不变
- 继续推进不受影响的后续步骤

### 2. 局部阻塞失败

如果某一步失败只影响后面的局部步骤，例如测试失败导致后续不能直接合并，那么更合理的做法是：

- 保留前面已经完成的有效步骤
- 以最近检查点为起点
- 重建受影响的后续步骤
- 从这个点继续执行

这应该是默认的失败处理方式。

### 3. 全局失效失败

如果失败意味着整张计划依赖的关键前提已经失效，例如目标变了、基线变了、关键依赖不存在了，那么才需要：

- 停止旧计划
- 进入全局重规划
- 必要时回退到更早检查点甚至起点

## 十二、增量重规划比整张重来更合理

我现在更倾向于把“修改计划”理解成一种增量重规划能力，而不是简单的“终止并全部重来”。

也就是说：

- 前面已经执行完成且仍然有效的部分应该保留
- 系统真正需要重建的是后面尚未完成或已经受影响的部分
- 新计划应当从“最后一个有效规划节点”继续往后生成

这套逻辑可以简单概括成：

- 主 Agent 先生成计划
- 用户确认后启动执行
- 执行到某个检查点
- 如果任务失败或用户要求调整
- 先判断影响范围
- 优先从最近有效检查点做局部重规划
- 再从该点继续执行后续步骤

这样做的好处是：

- 不会浪费已经完成的有效结果
- 更符合真实工程协作过程
- 更适合长任务和多 Agent 并行任务
- 用户也更容易理解系统到底“保留了什么，重算了什么”

## 十三、总结成几个最核心的要点

如果把整套设计压缩成最核心的几句话，我最想表达的是：

- 这个系统要把“开放式多角色群聊”和“内建专用子代理任务委托”结合起来。
- 用户既可以直接和所有子 Agent 聊天或发任务，也可以通过主 Agent 统一规划并控制子 Agent。
- 所有 Agent 都通过 `@` 被唤醒，交互入口应统一。
- 因为群聊历史不会清空、所有 Agent 共享消息流，所以必须设计非常强的记忆与压缩机制。
- 主 Agent 的调度应基于一张明确的计划表，由独立执行器从上到下推进。
- 同步任务必须串行执行，异步任务可以并发执行。
- 在执行过程中，用户仍然可以和主 Agent 交流、停止或修改计划。
- 一旦任务失败或计划需要调整，应优先基于最近检查点做增量重规划，而不是默认整张计划重来。
- 因为真正执行会消耗资源并影响工程状态，所以主 Agent 在执行计划前应先让用户确认。
