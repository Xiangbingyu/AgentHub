# Orchestrator 与多 Agent 群聊设计

## 一、设计目标

这套设计的目标，不是做一个普通的 AI 群聊，而是做一个可以承接真实工程协作的多 Agent 协同系统。

核心目标如下：

- 将“开放式多角色群聊”和“主 Agent + 内建专用子代理”两种模式结合起来。
- 用户既可以直接与任意子 Agent 对话、追问、下发任务，也可以通过主 Agent 进行统一规划、拆解和调度。
- 保留群聊式协作的自然体验，同时保留任务执行、状态跟踪和结果沉淀所需的秩序。
- 将群聊、任务、Workspace、Sandbox、Proposal、Git 流程打通，形成完整的工程协作闭环。
- 为长时、多角色、共享历史的群聊设计一套更强的记忆与上下文压缩机制。

## 二、核心协作模型

系统采用双层协作模型：

- 交互层：开放式多角色群聊
- 执行层：主 Agent 编排 + 子 Agent 异步执行

可以将其理解为：

- 群聊负责协作可见性
- 主 Agent 负责调度秩序
- 子 Agent 负责专门产出
- `@` 负责统一唤醒入口
- 任务系统负责执行态管理

也就是说，用户在同一个群聊中可以看到所有成员，和所有 Agent 交流，但系统内部仍然保留明确的职责分工和执行边界。

## 三、角色定义

### 1. 用户

用户是需求提出者、优先级决定者和最终审批者。

用户可以：

- 直接 `@` 某个子 Agent 提问或下发任务
- 直接 `@Orchestrator` 请求任务拆解、调度或汇总
- 在群聊中补充上下文、调整优先级、暂停任务、取消任务
- 审阅 Proposal、确认合并、决定是否继续推进下一轮任务

### 2. 主 Agent（Orchestrator）

`Orchestrator` 是群聊中的主 Agent，负责理解用户目标、拆解任务、分派子 Agent、协调执行顺序、跟踪进度并汇总最终结果。

主 Agent 的职责包括：

- 理解用户整体需求
- 将大任务拆成可执行子任务
- 判断任务之间的依赖关系和并行关系
- 选择最合适的子 Agent
- 管理任务状态、优先级和冲突
- 在群聊中持续汇报整体进度
- 汇总多个子 Agent 的结果并回传给用户

主 Agent 不应该默认承担大量具体编码工作，它更像项目经理和任务调度中心。

### 3. 子 Agent

子 Agent 是具体执行者，负责在特定专业领域内完成任务。

典型子 Agent 可以包括：

- `CodeAgent`：代码编写、重构、配置修改
- `DocAgent`：方案文档、说明文档、总结整理
- `TestAgent`：测试编写、测试执行、结果分析
- `ReviewAgent`：Diff 审阅、风险提示、合并建议

子 Agent 可以通过两种方式被唤醒：

- 用户直接 `@`
- 主 Agent 在任务编排中进行指派

## 四、统一唤醒机制

所有 Agent 的唤醒统一通过 `@AgentName` 完成。

规则如下：

- `@Orchestrator`：唤醒主 Agent，进入规划和调度模式
- `@某子Agent`：直接唤醒具体子 Agent
- 未显式 `@` 时：默认由 `Orchestrator` 接管，再决定是否需要分派给其他 Agent

这样设计的好处是：

- 用户只需要记住一种交互入口
- 聊天、提问、任务分发和调度都统一在同一消息语义中
- 系统后端可以更容易区分“谁被唤醒”“谁应该响应”“是否要进入执行态”

## 五、群聊中的两种交互模式

### 1. 直接对话模式

用户可以直接和任意子 Agent 对话。

例如：

- `@DocAgent 你觉得这段设计怎么表述更清楚？`
- `@CodeAgent 这个函数为什么会出现空指针？`

这种场景的特点是：

- 更像普通群聊中的定向提问
- 不一定生成正式任务
- 不一定进入异步执行态
- 可以作为讨论、澄清、追问、解释的一部分

### 2. 编排调度模式

用户也可以直接 `@Orchestrator`，让主 Agent 统一规划和调度多个子 Agent。

例如：

- `@Orchestrator 帮我把这个需求拆一下并安排人做`
- `@Orchestrator 先让人修前端，再安排测试，最后帮我汇总`

这种场景的特点是：

- 主 Agent 负责拆任务
- 主 Agent 决定任务分派对象和执行顺序
- 子 Agent 以执行者身份接任务
- 群聊中会出现更明确的状态更新和结果回流

## 六、任务模型

为了避免群聊中的所有事情都退化成“文本消息”，系统中需要显式引入 `Task` 作为结构化实体。

建议每个任务至少包含以下字段：

- `taskId`
- `title`
- `description`
- `creator`
- `assigneeAgentId`
- `taskType`
- `priority`
- `status`
- `workspaceId`
- `projectWorkspaceId`
- `sandboxId`
- `proposalId`
- `dependsOn`
- `createdAt`
- `updatedAt`
- `resultSummary`

### 推荐任务类型

- `code`
- `doc`
- `test`
- `review`
- `research`

### 推荐任务状态机

- `draft`
- `queued`
- `assigned`
- `accepted`
- `running`
- `paused`
- `blocked`
- `completed`
- `failed`
- `cancelled`

其中对用户可见的主状态可以简化为：

- 待分配
- 已接收
- 执行中
- 已暂停
- 已阻塞
- 已完成
- 已取消

## 七、主 Agent 的调度规则

主 Agent 不应该只是临时想到什么就派什么，而应该先形成结构化计划，再由独立的计划执行控制流负责推进。

换句话说，主 Agent 的核心能力不只是“分配任务”，而是：

- 生成计划
- 请求确认
- 启动执行
- 跟踪进度
- 接收用户控制指令
- 在必要时暂停、停止或重规划

### 1. 引入计划执行器（Plan Executor）

建议为主 Agent 单独设计一个计划执行器，而不是把所有调度都直接揉在群聊回复里。

这里不必在设计文档中绑定具体实现为操作系统线程，更合适的抽象是：

- `Plan Executor`
- `Execution Loop`
- `Plan Runner`

它代表的是一条独立的执行控制流，用于按照主 Agent 已经生成并确认的计划表，从上到下推进任务。

主 Agent 与计划执行器的职责划分如下：

- `Orchestrator`：理解需求、制定计划、解释计划、接受用户控制
- `Plan Executor`：按照计划表推进步骤、触发子 Agent、汇总执行状态

### 2. 主 Agent 可以做的事

- 创建新任务
- 拆分已有任务
- 生成完整计划表
- 为空闲子 Agent 分配新任务
- 给繁忙子 Agent 追加排队任务
- 调整任务优先级
- 暂停、恢复、取消任务
- 汇总当前全部 Agent 的工作进度
- 在用户要求下终止当前计划并进入重规划

### 3. 主 Agent 不应该直接做的事

- 与子 Agent 抢同一项具体执行任务
- 在没有必要时频繁打断正在工作的子 Agent
- 让多个子 Agent 同时维护同一条 Proposal Branch
- 在没有形成明确计划时就大规模调度多个子 Agent
- 在未获得用户确认的情况下自动执行高风险或复杂计划

### 4. 计划表模型

主 Agent 在正式调度前，应先生成结构化计划表。计划表中的每一步建议至少包含：

- `stepId`
- `title`
- `description`
- `assignee`
- `taskType`
- `mode`
- `dependsOn`
- `status`
- `expectedOutput`
- `rollbackStrategy`

其中最关键的是 `mode`：

- `sync`：同步步骤，必须按顺序逐步完成
- `async`：异步步骤，在依赖满足时可并发执行

### 5. 计划状态机

整个计划建议使用独立状态机，而不是完全复用单任务状态。

推荐状态包括：

- `draft`
- `awaiting_confirmation`
- `running`
- `paused`
- `replanning`
- `cancelled`
- `completed`
- `failed`

对应含义如下：

- `draft`：主 Agent 已初步生成计划，但尚未准备展示给用户
- `awaiting_confirmation`：计划已生成，等待用户确认
- `running`：计划执行器已启动，正在推进步骤
- `paused`：执行已暂停，保留当前状态
- `replanning`：用户要求修改计划，系统正在终止旧计划并生成新版本
- `cancelled`：计划被明确取消
- `completed`：所有步骤执行完毕
- `failed`：计划在执行过程中失败且未能自动恢复

### 6. 正式执行前必须确认

对于多 Agent 调度、跨文件修改、跨 Proposal 操作等复杂计划，建议主 Agent 在执行前先向用户确认。

确认前，计划处于 `awaiting_confirmation`，不得自动启动。

主 Agent 在确认阶段应至少向用户说明：

- 当前总目标
- 计划拆解结果
- 哪些步骤是同步串行
- 哪些步骤是异步并行
- 会唤醒哪些子 Agent
- 可能影响哪些文件、Proposal、Sandbox 或分支

可以保留一条扩展规则：

- 简单、低风险、小范围计划可自动执行
- 复杂、多 Agent、跨模块计划必须确认

### 7. 计划执行规则

计划执行器按计划表自上而下推进，但并不意味着所有步骤都必须完全串行。

推荐规则如下：

- 遇到 `sync` 步骤时，必须等待前置依赖完成后才能执行
- 遇到 `async` 步骤时，只要依赖满足，就可以与其他异步步骤并发执行
- 如果某个同步步骤依赖前面的异步结果，则必须等待对应异步步骤完成
- 如果多个异步步骤会修改同一高冲突区域，则即使标记为异步，也应降级为串行

可以理解为：

- 主线推进是线性的
- 局部执行可以并发

### 8. 用户在执行期间的控制能力

计划执行期间，主 Agent 仍然必须保持可交互，不能因为执行器在跑就失去对话能力。

用户应当可以持续与主 Agent 交流，并发出如下控制指令：

- 查询当前进度
- 暂停当前计划
- 恢复执行
- 停止整个计划
- 修改计划
- 调整优先级

也就是说：

- 计划执行是后台控制流
- 主 Agent 的对话通道始终保持前台可用

### 9. 暂停、停止与修改计划

建议明确区分三类控制动作：

#### `pause`

- 暂停当前计划推进
- 已运行中的子任务可根据策略继续执行到安全点，或被软暂停
- 当前上下文、状态和中间结果保留

#### `stop`

- 终止当前计划
- 未完成步骤进入 `cancelled`
- 当前计划整体进入 `cancelled`

#### `modify`

- 用户希望改变目标、顺序、分工或约束条件
- 当前计划进入 `replanning`
- 系统终止旧计划中未完成的步骤
- 根据回退策略回退到计划起点或最近检查点
- 主 Agent 基于最新要求生成新的计划版本
- 新计划再次等待用户确认后重新执行

### 10. 回退与检查点机制

当用户修改计划时，不应简单理解为“删除一切重来”，而应设计更细的回退策略。

建议每个计划步骤都带有 `rollbackStrategy`，例如：

- `discard`：直接丢弃临时结果
- `preserve_as_draft`：保留为草稿或废弃 Proposal
- `reopen_as_followup`：不回退，转化为后续修正任务
- `manual_revert_required`：必须人工确认如何处理

同时建议引入检查点机制：

- `plan start checkpoint`
- `milestone checkpoint`
- `pre-confirm checkpoint`

这样在用户要求修改计划时，系统可以回退到最近的安全检查点，而不是总是粗暴回到最初状态。

### 11. 与已有任务系统的关系

计划并不替代任务，计划是任务的上层编排结构。

可以理解为：

- 计划：控制执行顺序、依赖关系和整体目标
- 任务：承载单个子 Agent 的实际工作单元

因此：

- 一个计划可以包含多个任务
- 一个计划步骤通常会落成一个或多个任务
- 计划执行器推进的是步骤
- 子 Agent 实际执行的是任务

### 12. 建议的调度原则

- 有明确 `@某子Agent` 且任务清晰时，优先直派
- 无明确指派时，由 `Orchestrator` 自动分派
- 若任务间存在高冲突或前后依赖，则优先串行
- 若任务边界清晰且文件域独立，则允许并行
- 若计划涉及多 Agent 协作或高风险修改，则执行前必须确认
- 若用户中途修改目标，则旧计划应进入 `replanning`，而不是边执行边无约束漂移

## 八、子 Agent 的执行规则

### 1. 单 Agent 单热任务

同一子 Agent 在同一时刻只允许存在一个 `running` 状态的热任务。

这条规则非常重要，因为它是防止一个子 Agent 执行态混乱的底线。

### 2. 可以聊天，但不能并发执行第二个任务

子 Agent 在执行任务期间仍然可以：

- 在群聊中追问用户
- 汇报阶段进度
- 解释当前阻塞点
- 响应与当前任务有关的对话

但它不能在同一时刻接收第二个新的执行任务并立即开始并发工作。

也就是说：

- 可以继续说话
- 不能继续并行干第二个热任务

### 3. 新任务的处理方式

当一个子 Agent 正在执行任务时，如果又收到新任务：

- 可以进入 `queued`
- 可以由 `Orchestrator` 改派给其他 Agent
- 也可以由用户选择取消当前任务后切换

### 4. 执行必须绑定 Sandbox / Proposal

对于代码类和文档落地类任务，子 Agent 一旦进入执行态，应绑定：

- 对应的 `Workspace / Project Workspace`
- 对应的 `Sandbox`
- 必要时对应 `Proposal` 和 `Proposal Branch`

这样所有改动才能回到前面设计好的 Workspace 和 Git 流程中。

## 九、消息模型

群聊中建议区分不同类型的消息，而不是把一切都当普通聊天文本。

### 推荐消息类型

- 普通消息：讨论、提问、澄清、说明
- 唤醒消息：包含 `@` 的定向唤醒
- 任务消息：正式任务卡片
- 状态消息：已接收、执行中、阻塞、完成
- 结果消息：Proposal、Diff、测试结果、文档产出

这样做的目的，是让群聊既保留自然聊天体验，也保留工程协作的结构化可读性。

## 十、与 Workspace / Git / Sandbox 的关系

这套 Orchestrator 设计必须嵌在已有的 Workspace 和 Git 方案之上，而不是独立悬空存在。

关系如下：

- 群聊绑定 `Workspace`
- 任务落在某个 `Project Workspace`
- 每个代码任务在自己的 `Sandbox` 中执行
- 每个代码任务可以对应一个 `Proposal`
- `Proposal` 对应一个 `Proposal Branch`
- 最终结果通过 `Proposal Pool`、`Confirm`、`Version History` 回流到项目主线

也就是说，群聊只是入口，真正的工程落地仍然依赖前面已经设计好的 Workspace、Sandbox 和 Git Service。

## 十一、为什么必须设计更强的记忆机制

你的系统相比普通单 Agent 会话，有三个显著不同点：

- 群聊历史天然持续累积，不会像普通开发会话那样频繁新建 session
- 多个 Agent 共享同一条公共消息流
- 群聊中不仅有自然语言，还会混入任务、Proposal、Sandbox、测试结果、版本记录等结构化状态

因此不能再使用“把最近 N 轮聊天塞进上下文”这种普通做法，而必须采用分层记忆和动态压缩。

## 十二、记忆系统设计思路

### 1. 原始事件层

完整保留所有原始事件流，作为系统真相源。

包括：

- 用户消息
- Agent 消息
- `@` 唤醒记录
- 任务状态变化
- Proposal / Diff / Confirm / Push
- Sandbox 创建和销毁
- 测试结果
- 审批记录

这一层用于：

- 审计
- 回放
- 追溯
- 重新压缩

原始事件层不应该直接作为模型上下文输入。

### 2. 共享工作记忆层

用于描述群聊当前正在发生什么。

内容可以包括：

- 当前总目标
- 最近阶段性结论
- 当前活跃任务
- 当前正在执行的 Agent
- 当前阻塞事项
- 最近的关键用户要求

这一层是所有 Agent 可以共享的短期工作上下文。

### 3. 任务记忆层

这是整个系统最重要的一层。

相比“记住聊天内容”，系统更应该记住：

- 当前有哪些任务
- 每个任务是谁负责
- 现在做到哪一步
- 当前状态是什么
- 阻塞原因是什么
- 产出链接在哪里

每个任务都应该拥有自己的结构化记忆对象，而不是只散落在聊天记录里。

### 4. 项目知识记忆层

用于保存相对稳定、长期有效的信息。

例如：

- 项目技术栈
- 目录结构
- 代码规范
- 测试方法
- Git / Proposal / Sandbox 规则
- 用户长期偏好
- Agent 的分工规则

这一层不应该频繁重写，而是稳定增量更新。

### 5. Agent 私有工作记忆层

虽然群聊消息是共享的，但每个 Agent 仍建议保留私有工作记忆。

它用于保存：

- 当前任务的内部理解
- 临时计划
- 关注的文件集合
- 尚未公开的中间假设
- 下一步动作草案

这样可以避免所有 Agent 只盯同一份公共摘要，导致关注点互相污染。

## 十三、记忆压缩原则

### 原则 1：聊天历史永远保留

原始群聊历史应作为审计和回放真相源长期保留，不应该直接删除。

### 原则 2：上下文窗口不等于聊天历史

模型使用的上下文不应该直接等于历史聊天记录，而应由多层记忆动态拼装。

### 原则 3：状态优先于聊天措辞

系统应优先压缩和保留：

- 任务状态
- Proposal 状态
- Sandbox 状态
- 当前目标和结论

而不是优先保留所有自然语言细节。

### 原则 4：不是所有消息都进入高价值记忆

以下内容可以只保留在原始事件层：

- 寒暄
- 重复确认
- 短期噪音
- 无效试错

以下内容应优先进入结构化记忆或长期摘要：

- 用户明确要求
- 任务决策
- 技术约束
- 分工结论
- 风险说明
- 产出链接
- 状态变化

## 十四、压缩触发机制

压缩不建议只按固定消息条数触发，而应结合业务事件触发。

推荐触发时机：

- 创建新任务时
- 任务状态变化时
- 任务完成时
- Proposal 创建或 Confirm 时
- 用户改变总体目标时
- 群聊消息达到阈值时
- 子 Agent 长时间执行后恢复汇报时

这样压缩结果更贴合真实协作节点。

## 十五、上下文装配机制

当某个 Agent 被唤醒时，不应该简单读取整个群聊历史，而应动态组装上下文。

建议装配顺序如下：

1. 系统级规则
2. 当前 Workspace / Project 相关约束
3. 项目知识记忆
4. 当前任务状态
5. 与该 Agent 直接相关的最近消息
6. 最近阶段摘要
7. 必要的原始消息片段
8. 该 Agent 的私有工作记忆

不同 Agent 的上下文重点也应不同：

- `CodeAgent` 更关注代码、Proposal、测试和文件改动
- `DocAgent` 更关注设计结论、文案目标和输出格式
- `TestAgent` 更关注环境准备、测试要求和失败结果

## 十六、建议引入独立的记忆压缩器

为了让这套机制真正稳定，建议系统内部增加一个独立的记忆基础能力模块。

可以命名为：

- `Memory Orchestrator`
- `Context Compression Engine`

它和 `Orchestrator` 的分工不同：

- `Orchestrator` 负责任务和 Agent 调度
- `Memory Engine` 负责上下文提炼、摘要生成和上下文装配

它的职责包括：

- 监听群聊事件流
- 监听任务状态变化
- 自动生成阶段摘要
- 更新任务记忆
- 更新项目长期知识记忆
- 为每个被唤醒的 Agent 动态装配上下文

## 十七、当前设计中需要特别注意的点

### 1. 不要让所有 Agent 默认一起发言

虽然是开放式群聊，但如果所有 Agent 默认都抢答，群聊会迅速失控。

建议规则：

- 默认只有被 `@` 的 Agent 响应
- 默认只有 `Orchestrator` 可以在无人 `@` 时接管
- 其他 Agent 只有在被显式唤醒或被正式分派任务后才进入主动响应

### 2. 不要把“聊天”和“任务”混成一个状态

子 Agent 可以聊天，不代表它已经进入执行态。

应明确区分：

- 聊天响应
- 任务接收
- 异步执行

### 3. 不要把“共享聊天记录”和“共享全部执行态”混为一谈

共享的是公共消息流，不是每个 Agent 的内部思考和全部临时状态。

### 4. 不要只做普通聊天摘要

真正需要长期保留和稳定压缩的是任务状态、项目约束和执行结果，而不是一大段普通群聊总结。

### 5. 不要让主 Agent 既当项目经理又当主力执行者

主 Agent 可以少量参与执行，但默认职责仍应是规划、调度、协调和汇总。

## 十八、后续还需要继续细化的点

当前这版设计已经能形成主框架，但后续还需要继续细化：

- 子 Agent 的能力标签和选择策略
- 任务优先级和冲突规则
- 暂停 / 恢复 / 取消任务的控制权限
- Proposal 与任务的一对一或一对多关系
- 多 Agent 修改同一区域时的冲突策略
- 记忆系统的数据结构和落库方式
- 前端群聊中的任务卡片和状态展示形式

## 十九、一句话总结

这套方案的本质，是将“开放式多角色群聊”作为协作可见层，将“主 Agent + 内建专用子代理”作为执行调度层，并通过 `@AgentName` 统一唤醒；在此基础上，再通过任务系统、Sandbox / Proposal / Git 流程以及分层记忆压缩机制，把一个自然语言群聊真正升级为可承接工程协作的多 Agent 工作系统。
