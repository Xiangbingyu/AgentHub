# 数据库规范设计

## 1. 目标

这份文档的目标不是现在就落地 MySQL，而是先定义一套 **稳定的存储抽象规范**，满足两个要求：

- 开发阶段默认使用内存存储，便于在不同电脑上直接启动
- 后续切换到 MySQL 或其他持久化存储时，不改 API 层和主要业务逻辑

一句话：**先统一数据边界，再决定底层存储。**

---

## 2. 当前阶段的结论

当前阶段不要求落地 MySQL。

推荐方案：

- 接口层保持稳定
- Service 层只依赖 Repository 抽象
- Repository 默认先提供内存实现
- 后续再补 MySQL 实现

也就是说，当前开发阶段采用：

```text
FastAPI API
-> Service
-> Repository Interface
-> InMemory Repository
```

而不是：

```text
FastAPI API
-> 直接操作 MySQL
```

---

## 3. 设计原则

### 3.1 接口层不感知存储实现

路由层不应该知道当前是：

- 内存存储
- MySQL
- SQLite
- Redis

路由层只负责：

- 参数校验
- 调用 Service
- 返回响应

### 3.2 Service 层不直接写数据库

Service 层应只依赖 Repository 接口，不直接操作具体数据库客户端。

错误做法：

```text
service
-> import mysql client
-> 拼 SQL
```

推荐做法：

```text
service
-> repository.create_run(...)
-> repository.save_input(...)
-> repository.update_subtask(...)
```

### 3.3 先定义实体，再定义表

当前阶段先统一领域对象，不急着绑定关系型表结构。

最先要稳定的是这些实体：

- `AgentRun`
- `InputEvent`
- `Subtask`
- `Plan`

### 3.4 内存实现也要遵守持久化抽象

虽然当前用内存，但不能把内存实现写成随意的全局变量堆积。

内存版也应遵守：

- 明确的 Repository 接口
- 明确的主键规则
- 明确的查询方法
- 明确的状态更新方法

这样将来替换 MySQL 时，Service 层无需重写。

---

## 4. 当前推荐架构

```text
app/
├─ api/
├─ services/
├─ repositories/
│  ├─ interfaces/
│  │  ├─ agent_run_repository.py
│  │  ├─ input_event_repository.py
│  │  ├─ subtask_repository.py
│  │  └─ plan_repository.py
│  ├─ memory/
│  │  ├─ memory_agent_run_repository.py
│  │  ├─ memory_input_event_repository.py
│  │  ├─ memory_subtask_repository.py
│  │  └─ memory_plan_repository.py
│  └─ mysql/
│     ├─ mysql_agent_run_repository.py
│     ├─ mysql_input_event_repository.py
│     ├─ mysql_subtask_repository.py
│     └─ mysql_plan_repository.py
├─ models/
└─ schemas/
```

当前阶段只需要真正实现：

- `repositories/interfaces/*`
- `repositories/memory/*`

`mysql/` 可以先留空或后续补。

## 5. 核心实体规范

### 5.1 AgentRun

表示一次 Agent 运行实例。

建议字段：

```text
AgentRun
- run_id
- agent_id
- agent_kind
- workspace_id
- parent_run_id
- root_run_id
- status
- plan_path
- context_snapshot
- created_at
- updated_at
```

说明：

- `run_id` 是运行实例主键
- `agent_id` 指向具体 Agent
- `agent_kind` 由 `agent_id` 配置推导
- `parent_run_id` / `root_run_id` 用于主 run 和 worker run 的链路关联

### 5.2 InputEvent

表示一次输入事件。

建议字段：

```text
InputEvent
- input_id
- run_id
- source_type
- content
- idempotency_key
- created_at
```

说明：

- 用户输入和 worker 回调都统一抽象成 `InputEvent`
- `idempotency_key` 用于避免重复执行

### 5.3 Subtask

表示由主 Agent 分派出去的子任务。

建议字段：

```text
Subtask
- subtask_id
- root_run_id
- parent_run_id
- worker_run_id
- status
- task_prompt
- result_ref
- created_at
- updated_at
```

说明：

- `parent_run_id` 一般指向主 Agent run
- `worker_run_id` 是子 Agent 自己的运行实例

### 5.4 Plan

表示当前运行计划。

建议字段：

```text
Plan
- plan_id
- run_id
- workspace_id
- file_path
- status
- summary
- updated_at
```

说明：

 - `PLAN.md` 是用户可见的计划文件，必须保留
 - `Plan` 保留结构化状态，同时也保留对应的原始文档内容
 - 两者应保持同步，当前阶段可以先以内存实现为主，但语义上不丢原文档

## 6. Repository 接口规范

每个 Repository 应只负责一种实体，不要把所有数据操作都塞进一个“大仓库”。

### 6.1 AgentRunRepository

建议方法：

```text
create(run)
get_by_id(run_id)
update_status(run_id, status)
update(run)
```

### 6.2 InputEventRepository

建议方法：

```text
create(input_event)
get_by_idempotency_key(run_id, idempotency_key)
list_by_run_id(run_id)
```

### 6.3 SubtaskRepository

建议方法：

```text
create(subtask)
get_by_id(subtask_id)
list_by_parent_run_id(parent_run_id)
update_status(subtask_id, status)
update(subtask)
```

### 6.4 PlanRepository

建议方法：

```text
create(plan)
get_by_run_id(run_id)
update(plan)
get_raw_document(run_id)
save_raw_document(run_id, content)
save_plan_file(workspace_id, file_path, content)
load_plan_file(workspace_id, file_path)
```

注意：

- `PlanRepository` 负责 plan 的结构化状态和原始文档内容
- `PLAN.md` 仍然保留，作为 Workspace 里的可视化文件
- 当前阶段优先以内存维护 plan 和原文档，再同步写入 `PLAN.md`

## 7. 内存实现规范

开发阶段默认采用内存实现，但要有边界。

### 7.1 内存实现的目标

- 本地直接启动
- 不依赖外部数据库
- 方便联调接口和 Agent loop
- 方便在不同电脑上快速跑通

### 7.2 内存实现的约束

- 不能让路由直接操作全局字典
- 必须通过 Repository 接口访问
- 必须保持主键唯一
- 必须支持按 `run_id` 查询
- 必须支持幂等查询

### 7.3 推荐实现方式

```text
InMemoryStore
- agent_runs: Dict[run_id, AgentRun]
- input_events: Dict[input_id, InputEvent]
- subtasks: Dict[subtask_id, Subtask]
- plans: Dict[run_id, Plan]
```

必要时可再维护辅助索引：

```text
indexes
- input_by_run_id
- subtask_by_parent_run_id
- input_by_idempotency_key
- plan_by_run_id
```

### 7.4 内存实现的限制

- 服务重启后数据丢失
- 不适合多进程共享
- 不适合正式环境

因此它的定位只能是：

- 本地开发
- 接口联调
- MVP 快速验证

---

## 8. 未来切换 MySQL 的规范

后续切到 MySQL 时，应该满足：

- API 不改
- Service 不改
- Repository 接口不改
- 只替换 Repository 实现和依赖注入

也就是说，迁移路径应当是：

```text
MemoryRepository
-> MySQLRepository
```

而不是：

```text
重写路由
重写 service
重写业务流程
```

### 8.1 切换时机

推荐在这些条件满足后再切 MySQL：

- 核心接口稳定
- `AgentRun / InputEvent / Subtask / Plan` 字段基本稳定
- worker 回调链路跑通
- `PLAN.md` 同步逻辑稳定

### 8.2 切换方式

推荐通过配置切换：

```text
STORAGE_BACKEND=memory | mysql
```

然后由依赖注入层决定加载哪套 Repository。

---

## 9. 与 AgentRun 方案的关系

这份规范与 `backend-python/docs/AgentRun输入接口实现方案.md` 的关系是：

- `POST /agent-runs` 依赖 `AgentRunRepository`
- `POST /agent-runs/{run_id}/input` 依赖 `AgentRunRepository` 和 `InputEventRepository`
- `delegate_tool` 依赖 `SubtaskRepository`
- `plan_tool` 依赖 `PlanRepository`

也就是说：

- Agent loop 方案负责定义流程
- 数据库规范负责定义存储边界

两者要分层，但必须兼容。

---

## 10. 一句话总结

当前阶段最合理的存储方案不是直接接 MySQL，而是先以 Repository 抽象为边界、以内存实现为默认落地方式，把 `AgentRun / InputEvent / Subtask / Plan` 这套数据模型稳定下来；后续需要持久化时，再无缝切换到 MySQL。
